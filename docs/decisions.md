# Decisions, open questions & gaps

Status values:

- **Accepted**: decided by the owner.
- **Proposed**: a recommendation made in these docs that needs sign-off before the stage listed in *Needed by*.
- **Open**: no recommendation yet, or the decision needs owner input.

## 2. Open questions

From SAD §12, with recommendations:

| ID | Question | Recommendation | Needed by |
|---|---|---|---|
| O-1 | Container orchestrator | **Hybrid.** Run FreeSWITCH and OpenSIPs on dedicated hosts or VMs as containers with host networking. Large RTP UDP port ranges and real IP visibility are awkward under Kubernetes CNI networking. Run stateless services on Kubernetes, or on Nomad if the team wants one tool for both. Develop on Docker Compose until then. Keep services 12-factor so the decision stays cheap. | S4 |
| O-2 | CDR / billing API schema | A v1 draft is in [06 §cdr-service](architecture/06-services.md#cdr-service). Freeze it in S2-11 after review against one target billing system's import format. | S2 |
| O-3 | Speech-to-text provider | Keep it behind a `TranscriptionProvider` interface and evaluate on accuracy for telephony audio (8 kHz), price, data-residency options, and data-retention terms. The first adapter is picked in S5-06. | S5 |
| O-4 | XMPP server | **ejabberd.** It has mature clustering, many virtual hosts (one per tenant), MUC, MAM with SQL storage (MariaDB), external/HTTP auth, and an admin HTTP API for provisioning. Prosody is the lighter alternative if clustering isn't needed. | S6 |

## 3. Conflicts & gaps found in the SAD

| ID | Issue | Detail | Proposed resolution |
|---|---|---|---|
| **C-1** | Billing API vs. the reseller private-data wall | SAD §6 says the CDR/billing API lets **tenants/resellers** integrate billing, but SAD §3 says resellers have **no access** to tenant CDRs. Resellers usually do the billing. | Define a separate **billing record** (usage data class): tenant, call ID, start, billable seconds, direction, trunk ID, destination number or prefix. Leave out recordings, legs, caller names, internal extension detail, and SIP metadata. Resellers get this through a `billing.read` API key. Full CDRs remain tenant-private. **Owner to confirm** whether resellers may see the full destination number and whether tenants must opt in. |
| **G-1** | Emergency calling not addressed | A multi-line telephone system in the US is subject to Kari's Law (direct 911 dialing without a prefix, plus on-site notification) and RAY BAUM'S Act (dispatchable location). Other countries have their own rules. With BYO trunks, location delivery depends on each carrier's E911 service. | Minimum in core, in S2: direct dial without a prefix, a priority emergency route per tenant, an emergency location per extension, a notification hook (email/SMS/console) on every emergency call, and the configured location passed to the carrier in the format that carrier supports. **Owner to set the regulatory scope** (countries in scope for v1). |
| **G-2** | Voicemail on stateless nodes | Stock `mod_voicemail` stores on node-local disk, which breaks "any node serves any tenant". | D-009 (central storage), pulled into S2 (D-015). |
| **G-3** | Queues, parking, and conferences are per-node in FreeSWITCH | Active-active with non-pinned nodes still needs a single owner per live queue, lot, or room. | D-010 affinity leases. |
| **G-4** | Trunk registration with N nodes | If every FS node registered every tenant trunk, carriers would see multiple competing registrations. | D-007 (OpenSIPs `uac_registrant`, clustered). |
| **G-5** | Prompts, greetings, and MOH storage not addressed | These are tenant uploads needed on every node. | Media assets in S3, played through `http_cache` (pbx-config-service). |
| **G-6** | Toll-fraud controls not addressed | This is the largest operational risk for a PBX platform. | [07 §6](architecture/07-security-and-permissions.md#6-abuse--fraud-controls), in S2. |
| **G-7** | Email delivery has no owner | Voicemail-to-email, fax-to-email, and password reset all need email, with branding. | notification-service (D-014). |
| **G-8** | "LCR" with no shared carrier pool | LCR here can only mean choosing among a single tenant's own trunks (priority, prefix rules, failover). | Per-tenant `drouting` groups. |
| **G-9** | SMS on BYO carriers | SMS isn't carried over the SIP trunk for most carriers. It needs each carrier's API. | Adapter model (O-8). |
| **G-10** | Permission catalog has no read-counterparts for most `*.manage` verbs | [07 §3.3](architecture/07-security-and-permissions.md#33-permission-catalog) gives `master_support`/`reseller_support` "read everything"/"read config" access, but the catalog (`@cuc/authz`'s `PERMISSION_CATALOG`) has no `tenant.read`-shaped permissions to grant — only the `*.manage` verbs exist, which also imply write. Found while building the built-in roles in S1-06; the roles bundle what the catalog actually has rather than inventing permissions unilaterally. | **Owner to decide**: add a `*.read` permission alongside each `*.manage` one (roughly doubles the catalog), or redefine the two support roles' scope to name specific `*.manage` permissions they may use read-only via a route-level convention. Needed before S1-08 (api-gateway) or any route relies on `master_support`/`reseller_support` actually working as documented. |
| **G-11** | Org hard-delete (with retention window and data export) has no owning task | [02 §2](architecture/02-tenancy-and-branding.md#2-provisioning-responsibilities) documents the full lifecycle as `active` → `suspended` → `active`, and from either state → `pending_deletion` → `deleted` (hard delete after a retention window, with a data export offered first), but no stage task in the plan builds the export job, the retention timer, or the hard-delete worker. S1-02 implements create/read/update/suspend/resume only — its "Done when" text never mentions delete, matching this gap rather than contradicting it. | **Owner to decide**: schedule a task for the `pending_deletion` → `deleted` transition (export job, retention window, hard-delete worker) — most naturally alongside S5's retention-policy work ([S5-05](plan/implementation-plan.md)), since both need the same S3-lifecycle machinery. Until then, org-service's `suspend`/`resume` are the only lifecycle transitions implemented; nothing can reach `pending_deletion` or `deleted`. |
| **G-12** | `audit_events` partition maintenance and retention have no owning task | S1-07's migration creates monthly `RANGE COLUMNS` partitions on `at` for a multi-year window generated at migration-write time, plus a `MAXVALUE` catch-all so inserts never fail — but nothing rolls the window forward (adds next year's partitions before this one runs out) or drops partitions past [07 §4](architecture/07-security-and-permissions.md#4-audit)'s configurable retention (default 1 year). Every row still lands somewhere (the catch-all), so this is an efficiency/retention gap, not a correctness one. | **Owner to decide**: schedule a periodic job (most naturally alongside S5's retention-policy work, like G-11) that adds a partition for each upcoming month and drops/archives partitions older than the configured retention. |
| **G-13** | `audit.read`'s declared data class can't represent its actual, per-row mixed sensitivity | [07 §3.3](architecture/07-security-and-permissions.md#33-permission-catalog) lists `audit.read` as `config/private` — genuinely mixed, since one org's audit trail mixes ordinary config-change rows with rows about master's audited access to that org's private data. `@cuc/http`'s route-contract guard (rule 3) requires exactly one `dataClass` per route, and `GET /v1/orgs/:orgId/audit-events` declares `config` so `reseller_admin`/`reseller_support` (which hold `audit.read`) aren't blocked outright by H1's coarse, route-level wall — real filtering happens in the query (`actor_org_id = :orgId OR target_org_id = :orgId`), not the declared class. | **Owner to decide**: whether a route's dataClass should stay a coarse, route-level property (current model) or whether mixed-sensitivity endpoints like this one need per-row class evaluation at query time — which is what `h1PrivateDataWall`'s resource-aware form already does, just not reachable from a route that serves a heterogeneous result set. Needed before this route's H1 exposure is fully correct, not just query-filtered. |
| **G-14** | API-key authentication has no issuing/verifying endpoint | [06's api-gateway section](architecture/06-services.md#api-gateway) lists API-key auth as one of api-gateway's responsibilities, and S1-08's plan row names it explicitly, but identity-service — which [06](architecture/06-services.md#identity-service) names as the owner of API keys (`/v1/orgs/{orgId}/api-keys`) — has never built that endpoint across S1-05, S1-06, or S1-07; it remains listed there as future scope. There is nothing for the gateway to verify a presented key against. | api-gateway (this task) recognizes the `ApiKey` auth scheme and returns a distinct `501 api_key_auth_not_implemented` rather than either silently accepting it or folding it into a generic `401` — so a caller can tell "not supported yet" from "wrong key." **Owner to decide**: schedule identity-service's api-keys CRUD + verification lookup (most naturally alongside whichever stage first needs machine-to-machine API access, since nothing in scope through S1 requires it yet), then wire api-gateway's `ApiKey` branch to call it, matching the JWT branch's shape. |
| **G-15** | "All writes" and "all private/secret reads" audit coverage ([07 §4](architecture/07-security-and-permissions.md#4-audit)) is not implemented for ordinary CRUD, in any service | 07 §4 states plainly that every write and every private/secret read is written to `audit_events`. In practice, across org-service (S1-02/03/04), identity-service (S1-05/06), and now pbx-config-service (S1-09), only two call sites ever call `@cuc/audit`'s publisher: identity-service's `onUnscopedAccess` sink (cross-tenant queries only) and pbx-config-service's `:reveal` action (S1-09's own task text names it explicitly, so it was built for real rather than left to match this gap). Ordinary writes — creating a reseller, suspending a tenant, updating an extension's display name — produce a domain event but no audit event. | **Owner to decide**: whether every write across every service should call `recordAuditEvent` alongside its domain event (a cross-cutting retrofit, not one task's job) — most naturally done as its own stage-spanning task once enough services exist that the pattern is stable, rather than three separate services each guessing at the right shape independently. Until then, `audit_events` reliably covers cross-tenant reads and the one action (`:reveal`) whose task text required it, and nothing else. |
| **G-16** | telephony-config's reconciliation job (06: "compares the read model with the source services") can only check itself, not the source services | S1-12 built the `org.*`/`pbx.*` event-driven projection and a real reconciliation pass, but that pass only diffs telephony-config's own local read model against what is actually projected into the `opensips` schema — it repairs a failed or hand-edited `opensips` write, not a read model that itself drifted from org-service/pbx-config-service (e.g. a missed event that never redelivered). Neither upstream service exposes a "list everything" internal endpoint (org-service has `GET /internal/v1/tenants/:id/domain`, S1-09; pbx-config-service now has `GET /internal/v1/tenants/:tenantId/extensions/:id`, S1-12 — both single-record lookups, not listings), and building one well (pagination, at minimum) is its own piece of work. | **Owner to decide**: add paginated internal listing endpoints to org-service (tenants + primary domain + status) and pbx-config-service (extensions + digest credential per tenant), then extend `services/telephony-config/src/reconcile.ts` to diff against them too. Until then, an event that is silently lost before `consumed_events` records it (a crash between JetStream ack and commit is excluded by design, but a bug in the handler that returns early is not) has no automatic repair path. |
| **G-17** | CI's shared `TEST_NATS_URL` is unsafe once more than one service tests the same event subjects with a real bus | `.github/workflows/ci.yml` sets `TEST_NATS_URL` globally so every package's `vitest run` points at the *same* JetStream server — `packages/testing/src/nats.ts`'s own doc comment already names the risk this creates ("two suites sharing one server would fight over the same stream names," which is exactly why its preferred, unset-`TEST_NATS_URL` path spins up an isolated `nats-server` per suite instead). Through S1-11, pbx-config-service's `domain.consumer.test.ts` was the only test in the repository that published real `org.domain.added` events to a real bus, so the collision this predicts never fired. S1-12 added telephony-config's own `org.*`/`pbx.*` consumers under test, and turbo running both packages' `test` tasks concurrently against the shared CI server produced the predicted symptom twice: once as an inflated `pass.handled` count on a first pull, and — after loosening that assertion — again as a stray message landing on a *second*, otherwise-expected-empty pull in a `redelivery does not recompute/re-project twice` test. | Every affected `pass.handled`/`first.handled` assertion was loosened from `toBe(1)` to `toBeGreaterThanOrEqual(1)` (the tenant-specific outcome each test asserts afterward is unaffected by a stray unrelated event). The `redelivery does not [re]project/recompute twice` tests in both services no longer assert `toBe(0)` on a second pull at all — instead they name the exact event id published and check `consumed_events` has exactly one row for it, which is what the dedupe mechanism (an insert on `id`, its primary key) actually guarantees, and is immune to any other concurrent traffic on the shared stream. **Owner to decide**: whether to also stop setting `TEST_NATS_URL` in CI (each package isolates itself via its own spawned `nats-server`, at the cost of N spawns) or namespace test subjects/streams per CI job — the per-test fixes above remove the symptom but not the shared-server cause, which could still surface a novel flake somewhere neither fix anticipated. |
| **G-18** | Nothing seeds OpenSIPs' `dispatcher` table with the FS node pool, and `opensips.cfg.template`'s own comment claiming otherwise was aspirational, not implemented | 03 §1's "load balancing across FS nodes" and S1-11's `opensips.cfg.template` both assume a populated `dispatcher` table (`ds_select_dst(1, 4)`, the path a registered phone's outbound call takes to reach FS), and the file's own comment says "The FS set itself is provisioned as environment config" — but no script, migration, or compose seed step has ever written a row there. Through S1-12 this went unnoticed because no test exercised a live call end to end. S1-13's own real-FreeSWITCH verification (this task) surfaced it while confirming ext→ext dialplan routing: a registered phone's call never reaches FS at all today, in any deployment of this compose stack — `ds_select_dst` simply fails and the caller gets a 503. (Separately, S1-13 *did* add the other missing half of ext→ext — `route{}`'s "request from FS: lookup(location) and relay" branch, 03 §2.1 — since that one is squarely what this task's own dialplan response depends on to mean anything on a live call; this gap is the one piece deliberately left for its natural owner instead of expanded into here.) | **Owner to decide**: where FS-pool seeding belongs — most naturally `infra/compose`'s own dev/test bootstrapping (alongside `seed.sh`) for this stage, since production dispatcher management is presumably a future task's concern (dispatcher rows would eventually come from a real node-registry/health-check system, not a static seed). Needed before S1-14's live SIPp scenarios can complete a real call through the dispatcher path — S1-13's own "Done when" (the xml_curl endpoints, their XML shape, and the p99 benchmark) does not depend on it and was verified without it, by sending SIP directly to FS and directly to OpenSIPs rather than through the full trunk. |
